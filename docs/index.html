DESIGN.md

1. Overview & Initial Approach

Upon seeing the challenge, I understood it as a customer relationship management (CRM) tool for generating leads for a roofing supply distribution business, which meant there would be four sections involved: the data scraping and collection, the storing, processing, and retrieval of the data, the front-end user layer, and then the AI layer.

I started by creating the initial requirements in docs/OpeningRequirements.MD, and as I started asking questions and doing some research, I refined that into docs/SystemDesign.md.

2. Options Considered, What I Chose, and Why

Data Scraping & Collection

My opening requirements led me to a system that scrapes data off of GAF and combines it with other sources. Rather than running a live scrape every time a user searches a location, I chose to make it run primarily on a schedule (with an option for on-demand runs) and only update what has changed rather than redoing everything from scratch. If new parameters are added, only the things that rely on those parameters get updated, which saves a lot of compute and avoids rate limits.

Because GAF only gives basic info like certifications and ratings, I also chose to pull from contractor websites, Google Maps, the Better Business Bureau, and weather data sources. Depending on how big a company is, we want different contacts: for a smaller shop we just want the boss or owner, while for a bigger company we want an office or purchasing manager. Adding weather data also accounts for demand fluctuations. If there is a big storm, new-build roofing companies might be in a lull, whereas emergency and repair roofing companies will be booming and needing to order supplies beforehand.

Data Storage, Processing & Retrieval

From there, that data needed to be stored in a database. I considered NoSQL, but most of this data is very relational, and having a single source of ground truth that could be used relationally while inserting some JSONB columns for the non-SQL functionality I wanted was why I chose PostgreSQL. I also considered putting a dedicated search engine like Elasticsearch next to it, but Postgres indexes on the JSONB and tag columns (plus PostGIS for distance searches) kept filtering fast enough without running and syncing a second data store. Using JSONB also lets sales reps add their own custom fields (information slots) without needing to change the database schema, while custom tags live in their own small tables so the whole team can share them and filter by them.

I also had to make sure that when data is re-scraped, it doesn't overwrite changes or notes that the sales team manually made, and that multiple reps can edit or leave notes on the same lead with clear tracking of who did what. To handle that, I separated the scraped data from the manual user edits in the database.

I then created a series of TypeScript services to read, write, and filter the data. I considered keeping everything in one backend server, but splitting reads from writes means the heavy scraping and AI writes never slow down the reps' searches, and each side can scale on its own. Heavy searches also go through a queue that only lets a few run at once, so at peak load a rep might wait up to a second rather than the database getting overwhelmed. Because the system needs to scale to hundreds or thousands of reps, I added a read-only copy of the database alongside caching. At moments like 9:00 a.m. on a weekday, lots of sales reps will be hitting the database all at once trying to read their data, so routing reads to a read-only copy and cache takes that stress off the main database.

Front-End User Layer

I built a React frontend for the user to interface with the platform. I have previously worked with CRMs peripherally, so I knew generally how they worked. After doing a bit of research, I chose to emulate the layout and workflow of existing CRMs because that is what sales reps are already used to, so it integrates into their workflow much better.

It includes role-based views where a manager can see every lead and the whole team's activity, while an individual rep sees the leads allocated to them plus the unallocated pool, and can only edit their own. Reps start on a dashboard with an AI briefing of their territory, today's calls with a suggested pitch for each, their follow-ups (as a list or a calendar), new leads worth a call, and where their pipeline stands, with the lead map and local weather further down. In the list and profile views, I also made sure reps can create and toggle their own custom tags because they will eventually understand their business needs better than any developer, and I didn't want to overwhelm them with a million default tags.

AI Layer

For the AI layer, I split the work between pre-generated insights and on-demand chat so we aren't running heavy AI calls every time a page loads. After all of the data is scraped and organized, Gemini goes through it and pre-generates a summary, a recommended pitch, and talking points for each business based on its scraped data, website text, tags, and the reps' notes. I kept weather out of these per-lead calls on purpose: a cheaper rules-based layer turns weather alerts and storm reports into timing badges per county, so a storm never triggers hundreds of new AI calls. Weather does feed into the short AI briefing on each rep's dashboard. To keep the AI from making things up, every insight is checked before it's saved: it has to point to the facts it used, and anything that invents a certification or a contact, or promises something on the distributor's behalf, gets trimmed out or rejected.

I considered using Claude for the AI layer, which is what I'd use in production, but stuck with Gemini's free tier for the prototype and put both behind one model interface so switching is a configuration change rather than a code change.

Then, for the on-demand side, I added a chatbot in the bottom-right corner that has two main jobs: answering specific questions about a lead, and letting the user filter the list view using natural language (like saying "I'm looking for companies that have this trait" and having it control the UI filters for them).

3. Limitations & What I'd Do With More Time

When it came to the AI layer, I stuck with using the free version of Gemini, which did limit the quality of some of my insights and responses. With more tuning and a better model, the quality of the insights would greatly improve.

I could also get better data with more expansive search and scraping tools that require some budget, such as tools to find exact verified emails and deeper company information to feed into the large language models.

On the feature side, I would integrate proper notification and email support, as well as existing calendar functionality like Google or Microsoft Calendar. On the system design side, I would implement full geographical partitioning of the database, as well as better durability through automated backups and duplication.

docs/OpeningRequirements.MD

B2B Sales Intelligence Platform: System Design & Requirements

0. General Requirements & Assumptions

Functional Requirements

  • Role-Based Access & Lead Allocation: Sales reps view only the leads allocated to them plus the pool of unallocated leads (view-only), while managers have oversight across all reps and leads and are the only role that can allocate leads. A rep's territory is the set of leads allocated to them.
  • Location Search & Territory Dashboard: Users can view an overview of their territory (KPIs, map, weather/news) or search by ZIP code and radius.
  • Filtering, Sorting & Custom Tags: Users can filter and sort leads by system tags (size, age, GAF certifications, roof materials) or create their own custom tags and data slots.
  • Lead Profiles: Users can click a lead to view business details, size-appropriate target contacts, rep notes, weather context, and AI insights.
  • AI Summary & Recommendations: Profiles display pre-generated business summaries and actionable sales recommendations tied to real-world signals.
  • Action-Enabled AI Assistant: Users can ask a chatbot questions about a specific lead or use natural language to automatically filter and sort lead lists.

Non-Functional Requirements (Scale, Reliability, etc.)

  • High Scalability: The platform and pipeline must reliably support hundreds to thousands of concurrent sales reps, and data volumes well beyond the initial GAF roofing list as new industries and sources are added.
  • Fast Retrieval: Lead data and base AI insights are pre-generated and stored so searching, sorting, and dashboard loading feel instant.
  • Data Consistency & Concurrency: Overlapping location searches return deduplicated contractor records, and concurrent edits by multiple users (the allocated rep and managers) are tracked safely without overwriting each other.

Business & Persona Assumptions

  • Target User: An enterprise-scale roofing distributor supplying materials to roofing contractors.
  • Sales Workflow: Supports account planning for both net-new prospecting and existing account management.
  • Initial Scope: Scoped to a 25-mile radius around ZIP code 10013 using GAF contractor data as the primary seed source.
  • Single Distributor: One distributor uses the platform (single tenant), so access control is role-based within that one organization.
  • Industry-Agnostic Design: Roofing, with GAF as the seed source, is the first industry. Data sources and tag taxonomies are pluggable so the platform can extend to other industries and lead sources.
  • Production Design, Free-Tier Prototype: Everything is designed as a production system. For the prototype, paid services may be swapped for free tiers or free alternatives (with approval), and each swap notes what production would use instead.

1. Data Acquisition & Tagging

Requirements & Goals

  • Scheduled & On-Demand Runs: The pipeline runs primarily on a recurring schedule, with support for on-demand triggers by reps or managers (e.g., refreshing a territory or searching a new area). Duplicate requests for the same area are merged, and requests are rate-limited per user.
  • Location-Based Extraction: Given a location and radius, the system collects all roofing contractors, extracts their details, generates tags and notes, and triggers AI summaries.
  • User-Guided Customization: Reps can create custom tags and information slots. Slots are also passed into the pipeline to guide LLM extraction and insight generation; this is experimental and will be dropped if it doesn't work well.

Sources & Raw Data Scope

  • Primary Source: GAF residential contractor directory (ratings, certifications, years in business, location, contact info, roof types).
  • Secondary Business Sources: Contractor websites and public business listings to extract missing context and size-appropriate decision-makers (e.g., Owner/Boss for smaller shops vs. Office/Purchasing Manager for larger companies), defaulting to the owner when no other decision-maker can be found.
  • Contact Discovery: Better Business Bureau profiles supply owner and manager names and titles (personal-use profile scraping for the prototype; the paid BBB API in production). Hunter.io email discovery (domain search, email-pattern inference and verification) is planned for later.
  • Contextual Signal Sources: Weather/Storm APIs and local news feeds to track regional roofing demand drivers.

Tagging & Categorization Logic

  • Structured Tagging: Maps raw fields into filterable tags (GAF Master Elite status, rating tiers, years in business).
  • Service & Material Tagging: Extracts roof material specialties (metal, asphalt shingles, flat/TPO) and work types (new construction vs. storm/emergency repair).
  • Custom User Tagging: Supports rep-created tags and custom key-value data slots so the team can adapt categorization as business needs evolve.

Pipeline & Scaling Considerations

  • Incremental Updates: Avoids re-scraping or re-computing from scratch; only new or changed records, records past their source's refresh window, and records affected by newly added parameters are processed to save compute.
  • Audit Logging: All data additions, updates, and generated tags are stored with timestamped logs.
  • Rate Limiting & Queuing: Uses job queues to manage scraping and LLM rate limits safely when scaling across large territories.

2. Backend Storage & Retrieval

Requirements & Goals

  • Fast Storage & Retrieval: Store and retrieve contractor profiles, system/custom tags, and AI insights with structures optimized for fast multi-criteria filtering.
  • Rep Edits & Override Protection: Allow reps to add notes, create custom fields, and manually edit contact info, differentiating human edits from scraped data so future pipeline runs never overwrite rep changes.
  • Multi-User Collaboration & Attribution: The allocated rep and managers can work on the same lead at the same time, with clear attribution (user ID and timestamp) for every note, status change, and field edit. Notes are visible to anyone who can view the lead, and notes, edits and history stay with the lead when it is reassigned.
  • Role-Based Access Control (RBAC): Built-in auth to enforce manager vs. rep permissions and lead allocations: reps can act only on the leads allocated to them and can view (but not act on) unallocated leads, and only managers can allocate or reassign leads.

Data Schema / Entities

  • Companies (Core Entity): Stores an internal ID (source IDs such as GAF's live in a separate mapping), canonical business info, location coordinates, assigned rep, updated_in_last_poll, team-level last-checked/last-serviced timestamps, and scraped attributes. Per-rep checked/serviced state lives in a separate Lead Rep State table, and unchecked/unserviced are derived per rep and at the team level from these.
  • Manual Overrides: Rep edits to company fields and contacts live in a separate table that the pipeline never writes, so re-scrapes can't overwrite them.
  • Contacts: Stores multiple people per company, each with name, title, email, phone, source, confidence, email-verification status, and a do-not-contact flag.
  • Lead Allocations: Records which rep each lead is allocated to, which manager allocated it and when, with full history. Leads with no allocation form the shared unallocated pool.
  • Insights, Tags & Custom Fields: Stores pre-generated AI summaries, sales recommendations, system tags, and user-defined custom fields/tags linked to each contractor.
  • Users, Rep Notes & Audit Trail: Stores user roles (rep, manager) and links every note, checked/serviced action, and manual override to a user_id and timestamp. Account status (prospect, existing_customer, lapsed_customer, do_not_contact) comes from the distributor's CRM import, and each import is logged. Notes are append-only, and edits to shared fields use optimistic locking to prevent concurrent edit conflicts.
  • Ingestion Jobs / Logs: Tracks scrape timestamps, parameter versions, and pipeline run history.

Storage & Database Choices

  • PostgreSQL + JSONB: Use Postgres for relational integrity while leveraging JSONB columns for flexible, document-style data (allowing reps to add custom information slots dynamically without schema migrations; rep-created custom tags live in their own relational tables).
  • Microservices: Expose data and business logic through decoupled services, each owning one area:
  • API Gateway & Auth: authentication, rep vs. manager roles, and per-user rate limits.
  • Core CRM Write Service: rep notes, checked/serviced status, manual overrides, custom tags, and lead allocations.
  • Query & Filter Service: lead lists, filters, and profiles through the cache and read replicas, applying the visibility rule.
  • On-Demand AI Service: lead Q&A and natural-language filtering.
  • Ingestion & AI Pipeline: the Python workers for scraping, enrichment, tagging, and batch AI insights.
  • Event Bus: Services communicate through events (e.g., "pipeline updated lead", "rep edited field"), which also drive cache invalidation and dashboard updates.
  • Languages: User-facing services are written in TypeScript; the ingestion pipeline is written in Python.

Retrieval, Querying & Caching Strategy

  • SQL Indexing & Materialized Views: Use Postgres indexes (including GIN indexes for JSONB system tags and custom data slots) and materialized views to pre-compute team and manager dashboard KPI roll-ups.
  • Hot-Data Caching: Cache frequently accessed contractor profiles, popular territory queries, and dashboard KPI counters in an in-memory layer (e.g., Redis) to minimize database hits. Cached entries are invalidated through the event bus whenever the pipeline updates a lead or a rep edits one.
  • Read Replicas & Connection Pooling: Serve read-heavy traffic from Postgres read replicas behind a connection pooler (e.g., PgBouncer), with per-user rate limits at the API, so peak usage never overloads the primary database.

Future Scaling (Later)

  • Geographic Partitioning: Partition database tables by location/region while maintaining a single canonical source of truth so overlapping radius searches do not cause data desync. Deferred until data volumes require it.

3. Frontend User Interface

Requirements & Goals

  • Familiar CRM Paradigm: Designed around a standard CRM layout and workflow so sales reps can adopt it immediately.
  • Role-Based Views: Sales reps see their allocated leads, the unallocated pool, and their territory metrics, while managers can view and allocate leads across the entire team.
  • Customizable & Uncluttered: Reps can create custom tags and information slots while toggling which tags are displayed so the UI never becomes overwhelming.

Core Views & Rep Workflow

  • Territory Dashboard: Displays KPI counters (unserviced leads, unchecked leads, net-new updates from the latest poll), an interactive lead map, local weather/news summaries, and a territory-level AI briefing.
  • Multi-View Lead Lists: Filterable and sortable CRM list views where reps can slice leads by system tags, custom tags, certifications, and roof types.
  • Lead Detail View: Full contractor profile showing scraped company info, size-adjusted target contact (Owner vs. Office/Purchasing Manager), AI insights, rep notes, custom fields, and local weather impact.
  • Lead Allocation View (Managers): An unallocated queue where new leads from each pipeline run land, bulk assignment of a filtered list to a rep, and allocation suggestions (e.g., by ZIP code) that the manager reviews and approves.
  • Persistent AI Assistant: A floating chat widget in the bottom-right corner accessible across both the dashboard and individual lead profiles.

Key Features & Polish

  • Weather & Seasonality Demand Signals: Pairs local weather forecasts and storm alerts with contractor specialties (e.g., flagging repair/emergency roofers as high priority for supply orders before/after severe storms, while noting weather lulls for new-build contractors).
  • Natural Language UI Control: Reps can tell the chatbot what kind of companies they are looking for, and the assistant automatically applies the matching filters and sorts to the list view.
  • Update & Activity Highlights: Visual badges showing what data changed in the most recent pipeline poll and quick toggles to mark leads as checked/serviced.

4. AI Tools & Insights

Requirements & Goals

  • Hybrid Execution Model: Split AI workloads between pre-generated batch insights (computed during data ingestion) and on-demand interactive assistance (triggered by the user in the UI).
  • Actionable Sales Focus: Move beyond generic company descriptions to provide timing-aware sales recommendations and direct UI control.

Inputs & Context

  • Contractor Context: GAF profile attributes, scraped website content, company size, service/material tags, and rep-authored notes/custom fields.
  • Environmental Context: Local weather forecasts, severe storm alerts, seasonality, and regional roofing news.

Generated Outputs (Insights, Scoring, Recommendations)

  • Pre-Generated (Pipeline Phase):
  • Structured Extraction & Tagging: Parses unstructured website text to identify target decision-makers, roof material specialties, and custom user-requested fields.
  • Lead Summaries & Pitch Recommendations: Generates a concise business overview and a recommended sales angle (e.g., pitching bulk shingles to a high-volume GAF Master Elite roofer, or emergency tarps/repair stock to a storm-restoration contractor); weather timing comes from the separate weather timing layer.
  • Territory Briefing: Summarizes major changes from the latest data poll and weather-driven opportunities for the rep's dashboard.
  • On-Demand (Interactive Chatbot Phase):
  • Lead Q&A: Answers specific rep questions about an individual contractor using their stored profile, scraped text, and team notes as context.
  • Natural Language Filtering (Tool Calling): Translates conversational requests (e.g., "Show me Master Elite contractors doing metal roofs near 10013 that I haven't checked yet") into structured filter state updates that directly control the UI list view.

Execution & Cost/Scale Strategy

  • Batch Pre-Computation & Delta Processing: Run summary and extraction prompts asynchronously during pipeline jobs, and only re-run LLM calls when underlying contractor data, rep notes/custom fields, user-defined parameters, or the prompt/model version actually change.
  • Separate Weather Timing Layer: Weather and storm context is handled by a cheaper, rules-based timing layer per county that is joined at read time, so weather changes never re-run per-lead LLM calls.
  • Scoped Context & Function Calling: Keep on-demand chatbot latency and token costs low by scoping lead Q&A strictly to the active contractor's record, and using lightweight LLM tool/function calling to translate natural language search queries into the shared lead filter parameters. The assistant runs with the requesting user's permissions, so it can only see and filter leads that user can view.
  • Provider-Agnostic Models: One model interface supports multiple LLM providers (e.g., Anthropic Claude, Google Gemini), selected by configuration and API key.

System Design: B2B Roofing Sales Intelligence Platform

1. Overview

A B2B lead intelligence platform for a single enterprise roofing distributor (single tenant, so there is no tenant ID; access is role-based within one organization). The system scrapes contractor data (seeded from GAF around ZIP 10013), enriches it with public business registries, company websites and local weather/news, and pre-generates sales insights. It uses a Primary/Read Replica (CQRS-style read/write split) database architecture to separate heavy asynchronous scraping/AI writes from fast, read-heavy CRM queries across thousands of reps. The design is industry-agnostic: roofing with GAF is the first industry, and every lead has an internal ID that doesn't depend on the source that found it.

3. Requirements

Functional

  • Role-Based Access: Reps see the leads allocated to them (their territory) and can view, but not act on, unallocated leads. Managers see every lead and are the only ones who allocate or reassign leads.
  • Dashboard: Shows KPI counters (unserviced, unchecked, updated in last poll), a map of the rep's leads, weather/news alerts, and a territory AI summary.
  • Filtering & Custom Fields: Filter by system tags (size, age, GAF certs, roof materials), segment, priority score and account status, or by custom tags that reps create and custom data slots.
  • Lead Profiles: Displays company details, size-based target contacts (Owner for small shops vs. Office/Purchasing Manager for larger companies, falling back to the owner), rep notes, weather context, and AI sales pitches. Notes are visible to anyone who can view the lead.
  • Lead Allocation (Managers): An unallocated queue for new leads, bulk assignment of a filtered list to a rep, and allocation suggestions that the manager approves.
  • AI Chatbot: Answers questions about specific leads and translates natural language queries into UI list filters, under the same visibility rules as the user.

Non-Functional

  • Read-Heavy Scalability: Supports thousands of reps via PostgreSQL Read Replicas, connection pooling (PgBouncer) and Redis caching so heavy reads never block writes.
  • Override Safety: Pipeline re-scrapes never overwrite manual rep edits.
  • Multi-User Attribution: Notes and edits track user_id and timestamps with optimistic locking to prevent edit collisions.
  • Delta Processing: Scrapers and LLMs reuse stored results within each source's refresh window and only reprocess records whose inputs changed, to save compute.

4. Data Pipeline (Ingestion & Tagging)

  1. Triggers: Runs on a recurring schedule (cron) or on-demand when a rep/manager requests a territory refresh (or searches a new area) or adds a new custom extraction field. Duplicate requests for the same area are merged into one job, and requests are rate-limited per user. Jobs go through a database-backed job queue (Postgres with SKIP LOCKED claiming; today's offline pipeline also runs it on SQLite until the Postgres move) with retries and backoff, a dead-letter state and duplicate-job rejection. Per-host rate limits are enforced in each worker's HTTP client; in production they are shared across workers through a Redis token bucket.
  2. Scrapers: Pulls base attributes from the GAF directory, enriches from public registries (NY corporations, NYC contractor licences, USDOT/FMCSA), finds decision-makers through Better Business Bureau profiles (owner/manager names and titles), and crawls contractor websites for material specialties (metal, shingle, flat/TPO), work types (new construction vs. storm repair), and target contacts. Hunter.io email discovery is parked for later.
  3. Environmental Signals: Pulls regional weather forecasts/storm alerts and local roofing news per county. These feed a separate, cheap timing layer and never trigger per-lead LLM calls (see §7).
  4. Delta Check: Within each source's refresh window (GAF profiles 7 days, enrichments 30 days), a stored result is reused unless its input_hash changed; after the window it is refreshed, and errors are always retried. content_hash flags which GAF listings changed, for change tracking and the audit log. LLM insights re-run only when their input_hash changes. A run that reads fewer results than expected is marked partial and doesn't mark leads as delisted or changed. All pipeline outputs write strictly to the Primary Write DB. - When a material field changes, the Delta Engine sets last_material_change_at. At the end of a complete run, it sets updated_in_last_poll for the leads that run covered (true if new or changed). - When a company is first created, its county_fips is set from its location (PostGIS point-in-polygon against Census county boundaries).
  5. Tagging: A deterministic rules engine turns raw fields into system tags (each with a reason and source), a segment (strategic / growth / emerging / long tail) and a 0–100 priority score.

5. Backend & Database Architecture

  • CQRS / Read-Write Split:
  • PostgreSQL Primary (Write Store): Handles all pipeline ingestion writes, LLM insight writes, and rep mutations (notes, status changes, manual overrides, allocations).
  • PostgreSQL Read Replicas (Read-Only Store): Asynchronously replicates from the Primary DB (materialized views are refreshed on the Primary and replicate like any table). All dashboard loads, territory filtering, and chatbot context lookups hit the Read Replicas to isolate read traffic from write load. After a write, that user's reads go to the Primary for a few seconds so their own edit never seems to disappear.
  • PostgreSQL + JSONB + PostGIS: Stores core relational data alongside JSONB columns for scraped attributes, system tags and custom data slots (system tags and custom data slots GIN-indexed), so new fields need no schema migrations. PostGIS handles radius searches. Geographic partitioning is deferred until data volumes require it.
  • Redis: Caches hot lead profiles, common filter queries and KPI counters, and holds per-user rate-limit counters. Entries are invalidated by events whenever the pipeline or a rep changes a lead. Rep-specific cache keys include the user ID so one rep's results are never served to another.
  • Event Bus: Every write inserts an event into an outbox_events table in the same transaction; a relay publishes it to Redis Streams. Services subscribe to the events they need (e.g., the AI service consumes lead.updated), and the same events drive cache invalidation and live UI updates. Consumers are idempotent. Production can swap in Kafka or SNS+SQS.
  • Override Protection: The pipeline only writes scraped values. Rep edits go to a separate field_overrides table that the pipeline never touches, covering both company fields and individual contacts. The read layer shows the override when one exists, otherwise the scraped value. If the scraped value changes after a rep's edit, the profile flags "source changed since your edit".
  • Concurrency: Notes and activities are append-only, so they can't conflict. Edits to shared fields use optimistic locking: the client sends the version it read of the company or contact, and a stale write is rejected with the current value and who changed it. An override write supersedes the field's current override and checks that version in the same transaction; at most one active override exists per field.

Lead State

  • Checked (per rep): The rep marked the lead reviewed after its last material change (tier, certifications, rating, contact info, website). A material change makes it unchecked again.
  • Serviced (per rep): The rep logged a call, email or visit.
  • Team level: Checked or serviced by any rep. The CRM Write Service updates companies.team_last_checked_at / team_last_serviced_at in the same transaction as the per-rep lead_rep_state write.
  • Updated in last poll: New, or materially changed, in the most recent complete pipeline run.
  • Account status: prospect, existing_customer, lapsed_customer or do_not_contact, from the distributor's CRM import.

Rep View, notes, checked/serviced, activities, overrides, custom tags View only (including notes) No access
Manager Everything Everything + allocate Everything + reassign
  • Notes, overrides, custom tags and activity history stay with the lead when it is reassigned.
  • Allocate and reassign write the lead_allocations history row and companies.assigned_rep_id in the same transaction, so the two never drift.
  • One visibility rule is applied on every read path: lists, profiles, search, exports, cache and AI tools.

CREATE INDEX ON companies USING GIN (custom_fields jsonb_path_ops);

-- Team/manager roll-up: REFRESH MATERIALIZED VIEW CONCURRENTLY on the Primary every few minutes;
-- replicas serve the replicated result.
-- Per-rep counters: COUNT over companies WHERE assigned_rep_id = :me LEFT JOIN lead_rep_state (company_id, :me);
-- unchecked = checked_at IS NULL OR checked_at < last_material_change_at; unserviced = serviced_at IS NULL.
-- Cached in Redis per user.
CREATE MATERIALIZED VIEW team_dashboard_kpis AS
SELECT
    assigned_rep_id,                                         -- NULL row = unallocated pool
    COUNT(*) AS lead_count,
    COUNT(*) FILTER (WHERE team_last_serviced_at IS NULL) AS unserviced_count,
    COUNT(*) FILTER (WHERE team_last_checked_at IS NULL
                        OR team_last_checked_at < last_material_change_at) AS unchecked_count,
    COUNT(*) FILTER (WHERE updated_in_last_poll) AS recent_updates_count
FROM companies GROUP BY assigned_rep_id;
CREATE UNIQUE INDEX ON team_dashboard_kpis (assigned_rep_id);  -- required for CONCURRENTLY

-- with this schema. The existing contractors table becomes companies + company_source_ids (source = 'gaf'),
-- and existing contacts rows migrate into the new contacts table.

6. Frontend UI Workflow

  • Dashboard View: Displays top-level KPI counters (served from Read Replicas/Materialized Views and Redis), a map of assigned leads, local weather/news, and a daily AI territory briefing.
  • CRM List View: Sortable table (priority score by default) showing each lead's top ranking reasons, with toggleable tag visibility so custom tags do not clutter the screen, and a My Leads / Unallocated switch.
  • Lead Profile View: Shows merged contact info (with badges indicating rep-edited fields and "source changed since your edit"), pre-generated AI insights, weather demand impact, custom slots, and the multi-user notes feed.
  • Allocation View (Managers): The unallocated queue, bulk assignment of a filtered list, and suggestions to approve.
  • Persistent AI Widget: Floating bottom-right chat drawer accessible across all views.

7. AI Engine

  • Batch Pre-Generation (Pipeline):
  • Extracts structured tags and custom slot values from unstructured website text (custom slots are experimental and will be dropped if extraction quality is poor). LLM-extracted slot values are stored under scraped_attributes; a rep's correction goes through field_overrides.
  • Generates a business summary and sales pitch from the stored company facts, rep notes and custom fields. These are regenerated only when input_hash (those inputs + prompt version + model) changes.
  • Weather Timing Layer (separate and cheap):
  • Per county, rules combine active alerts and storm history with each lead's specialties into a timing badge and a one-line reason (e.g., pitching emergency repair stock to storm-restoration roofers before a storm, while flagging weather delays for new-build contractors).
  • Computed on a schedule per county and joined at read time, so weather changes never regenerate summaries.
  • Model Providers: One model interface over multiple providers (e.g., Anthropic Claude, Google Gemini), selected by configuration and API key, so the batch pipeline and the assistant can switch models without code changes.
  • On-Demand Assistant (UI):
  • Profile Q&A: Answers rep questions by reading only the active lead's profile and notes through the Query service, which rejects leads the user can't view.
  • UI Filter Control: Uses LLM tool calling (applyListFilters) to convert natural language requests into a LeadFilter. The Query service applies the user's visibility rule, so the assistant can never show leads the user can't see.

8. Deployment

  • Production: Built to be hosted. Every service and worker is a container; Postgres (primary + replicas) and Redis are managed services; secrets live in a secrets manager.
  • Security (production): Single sign-on via OIDC, with Postgres row-level security as defence in depth behind the visibility rule.
  • Local: docker compose up runs Postgres, Redis, the services, the web app and the pipeline worker, seeded from data/leadmaker.db.
  • Prototype swaps (approved): BBB profile scraping (production: BBB API); Google Places keyless map link (production: Places API key); a single Postgres primary (production: primary + replicas + PgBouncer); Gemini API free tier for all AI features (production: Anthropic Claude, Haiku 5.5 for batch work, via the same model interface). Any other paid-to-free swap needs approval.

Performance and numbers

Highlights - At 100k leads and about 200 req/s, search p95 dropped from about 9.6 s to 199-301 ms after tuning (target 300 ms). - 2,885 automated tests pass, including 43 end-to-end scenarios on a stack built from empty volumes. - The AI eval set (102 cases) passes offline, and 24 of 25 live cases pass on Gemini 3.5 Flash-Lite. - Assistant answers take 1.4-2.9 s, down from 12-47 s before the model switch.

Load test at 100k leads

The tests ran on one laptop in Docker: 8 vCPUs, default Postgres memory settings, and a single Postgres primary. The read replica was added later and isn't in these numbers. scripts/perf/synth.mjs fills a separate database with 100,000 synthetic companies and 2,200 users. scripts/perf/matrix.sh then runs 500 virtual users with a 2.5 s think time, about 200 req/s, which is the design load. Values are p95 in milliseconds. The raw runs are in scripts/perf/results/.

Three changes did most of the work: - Indexed generated columns for tags and founding year. Single-user search queries went from up to 1,074 ms to at most 34 ms. - A search limiter. 8 searches run at once, up to 32 more wait at most 1 s, and anything beyond that gets a fast "try again" instead of piling up. - List caches invalidated only for the scopes a write touches.

Runs vary on a shared laptop, and write-heavy runs sit right at the 300 ms target. One known slow spot remains: a manager's facet counts across all 100k leads take about 8 s and time out. The 424-lead demo isn't affected.
